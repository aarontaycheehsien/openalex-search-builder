# OpenAlex Search Builder

Deliver a tested search strategy for human peer review. Use the Python CLI from this skill directory. Every command takes `-w PATH` before the subcommand. Every measurement must come from its JSON output. If an API call fails, identify the incomplete step and resume it when possible.

1. **Intake.** Collect the question, eligibility criteria, any required limits, optional known DOIs, PMIDs or OpenAlex work IDs, and depth (quick, standard, thorough). Run `init --question "..." --eligibility "..." --depth standard`. For an update, use the existing workspace and inspect its last report and subsequent changes.
2. **Scope.** Propose a short table of concepts, their search, optional or screening role, and the rationale. Ask the reviewer to confirm or revise unless they have authorized proceeding. Keep outcomes, methods and population restrictions at screening when searching them would lose eligible studies. Put the blocks in `strategy.json`, the eligibility in `protocol.json`, and only justified limits in `strategy.json`. Record the decision with `scope --confirm --note "..."`. Changes to roles, rationale, protocol or limits need an updated decision.
3. **Known works.** Use `resolve --role seed --source "reviewer" ID ...`. If enough papers are available, allocate a holdout before reading the papers or mining vocabulary and register its identifiers as `validation`. Keep eligible included studies from a prior review as `benchmark` only when protected from strategy development. During a blind benchmark evaluation, follow its intake rules and keep the source review inaccessible. When quick runs lack seeds, proceed and document the evidence gap. At standard and thorough depth, look for independent relevant works, pilot targeted queries with `sample`, and follow references or citing works of screened development papers with `neighbors`. Check candidates against eligibility with `screen BATCH WORK_ID include|exclude|unclear --reason "..."`. Citation neighbors require screening. Record whether each route depended on the starting search. If a protected record informs revision, run `develop KEY --reason "..."`.
4. **Vocabulary.** Use `terms` on development records. Inspect their titles, reconstructed abstracts, recurring phrases and OpenAlex keywords. Consider synonyms, acronym ambiguity, spelling and indexing gaps. Start with `title-abstract`. Pilot keyword coverage by changing selected fields to `title-abstract-keywords`, rerunning and comparing both versions. OpenAlex keywords are assigned terms. A PubMed heading imported as text loses controlled-heading explosion. Spell out relevant alternatives. Keep term provenance and reasons for revisions in the critique or a workspace decision log.
5. **Run and revise.** Run `validate`, inspect the canonical OQL, then run `eval`. Check each block's count and known matches, the effect of dropping it, optional-block gains/losses, and failures due to eligibility limits. Compare result size and retrieval across revisions. Screen a seeded random sample for ambiguous terms and excess workload. Revise one cause at a time and rerun. In thorough mode also try alternate concept boundaries and examine citation discoveries from both directions. Held-out answers live in the evaluation archive for final scoring. Keep them out of development. Record missing abstracts and unresolved identifiers. A zero denominator gives no recall estimate.
6. **Critique.** Give a fresh-context reviewer the question, eligibility, strategy, development-only CLI evaluation, sample decisions and limitations. Use a separate human reviewer when fresh agent context is unavailable. Ask them to assess the six domains shown below, including changes made or reasons for acceptance. Review the API warnings. A legacy URL conversion warning can coexist with valid OQL. Record substantive uncertainties. Resolve required revisions, reevaluate, and review the new evidence. Submit a JSON file with `review critique.json`. A fresh-context assessment by an agent is an internal PRESS-structured critique. Formal peer review is a human step.
7. **Deliver.** Run `report`. It reexecutes the query, checks the critique against the live search interpretation and known-paper matches, and saves a dated audit and validation evidence. Hand over the report path, query, count, coverage and relative recall by set, unresolved identifiers, misses and limitations. Explain that a dated rerun queries the current OpenAlex index. Do not infer absolute recall from known-study retrieval.

## Strategy format

Copy `examples/telehealth.json` as a starting point. Use an OR list of terms per block. Search blocks are ANDed. Optional blocks are tested individually alongside the core. Screen blocks stay in the scope table. Each block has a unique ID, role, field, terms and rationale. Supported fields are `title`, `abstract`, `title-abstract`, and `title-abstract-keywords`. A term may be a single word, wildcard, quoted phrase or stemmed quoted phrase. In JSON, an exact phrase looks like `"\"remote care\""` and a stemmed phrase looks like `"stemmed \"remote care\""`. Limits support ISO `from_date` and `to_date`, and lists of `language` and `type` codes. Preview the canonical interpretation when using wildcards, stemming or phrases.

## Critique format

Supply a JSON object with text for `scope`, `vocabulary`, `boolean_and_fields`, `limits`, `retrieval`, and `limitations`. In each, describe the finding, supporting observation and disposition. Set `decision` to `ready` after addressing required changes. The CLI records the evidence fingerprint and repeats evaluation on delivery.
