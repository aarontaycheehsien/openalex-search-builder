# OpenAlex Search Builder

Deliver a tested search strategy for human peer review. Use the Python CLI from this skill directory. Every command takes `-w PATH` before the subcommand. Every measurement must come from its JSON output. If an API call fails, identify the incomplete step and resume it when possible.

1. **Intake.** Collect the question, eligibility criteria, any required limits, optional known DOIs, PMIDs, PMCIDs or OpenAlex work IDs, and depth (quick, standard, thorough). Run `init --question "..." --eligibility "..." --depth standard`. For an update, use the existing workspace and inspect its last report and subsequent changes.
2. **Scope.** Propose a short table of concepts, their search, optional or screening role, and the rationale. Ask the reviewer to confirm or revise unless they have authorized proceeding. Keep outcomes, methods and population restrictions at screening when searching them would lose eligible studies. **Never positively enumerate an "any X" facet** (such as "any exposure/stressor", "any outcome", or "any population") as an ANDed search block unless a single-concept search is genuinely unscreenable (>50k); enumerating open-ended facets leaks studies that use unpredicted terms. Calibrate target screening volume to topic breadth (a narrow clinical/SE review may screen 1k–5k records, whereas a broad cross-species or "any exposure × any outcome" review legitimately requires 15k–50k+ or an explicit sensitivity/workload decision—do not prune core synonyms solely to fit an arbitrary <10k ceiling). The converse also holds: a broadening must earn its records. In blind benchmark reruns (2026-11-26) breadth guidance alone produced 36% more records for 3 more gold works out of 135. When `eval` reports `revision.warning` (`broadening_without_gain`: the search grew by more than 20% and 500 works without gaining a development work), run `sample --added --size 10` and screen it; keep the broadening only if it recovers a known work or the added records include eligible ones, and record that evidence in the critique. Put the blocks in `strategy.json`, the eligibility in `protocol.json`, and only justified limits in `strategy.json`. Choose the corpus with the reviewer: `core` by default, or `all` to include OpenAlex's expansion corpus. Also decide whether retracted, withdrawn and removed works stay out (`"pulled": "exclude"`, OpenAlex's default view) or come in (`"include"`), for example when the review must identify retracted studies. Record the decision with `scope --confirm --note "..."`. Changes to blocks or their roles, the protocol, limits, corpus or pulled setting need an updated decision; rewording a rationale does not. If `eval` refuses, its message names what changed and the command to run.
3. **Known works.** Use `resolve --role seed --source "reviewer" ID ...`. If enough papers are available, allocate a holdout before reading the papers or mining vocabulary and register its identifiers as `validation`. Keep eligible included studies from a prior review as `benchmark` only when protected from strategy development. During a blind benchmark evaluation, follow its intake rules and keep the source review inaccessible. When quick runs lack seeds, proceed and document the evidence gap. At standard and thorough depth, look for independent relevant works, pilot targeted queries with `sample` (e.g. `sample --oql 'get works where title-abstract has ("open access" and citation) and publication_date <= 2020-12-31' --size 15`, or `sample --from-strategy --size 20` to sample the active `strategy.json`), and follow citing, referenced, or related works of one or multiple screened development papers with `neighbors` (accepts one or more Work IDs—multi-seed calls deduplicate and rank co-linked candidates first; supports `--size` > 100 via cursor paging, `--all`, `--max-pages`, and single-seed `--cursor`). **In seedless runs, break the keyword echo chamber:** discover candidates via `neighbors` (`references` and `citing`) from older or distant papers rather than keyword `sample` alone. For blinded validation, use the separate reviewer workflow below before finalising the strategy. If a separate reviewer is unavailable, allocate selected newly screened candidates directly with `screen BATCH WORK_ID include --role validation --reason "..."`; their content has already been seen, so call them protected, not blinded. Do not relabel an existing development record as validation. Citation neighbours come from OpenAlex's matched references (`referenced_works`): about 82% of references to works in OpenAlex are linked, unmatched ones are dropped and many records have no reference list, so older works, reports and theses are under-linked. `neighbors` shows each seed's matched-reference and citation counts and refuses a seed that has none in the chosen direction. Follow `references` from recent open-access papers (OpenAlex reads their reference lists from the PDF) and `citing` from older ones. `--direction related` is different: at most 10 nearest neighbours by text similarity, never reviews or retracted works, so treat it as a text route like keyword search, not citation searching, and do not rely on it when the eligible studies are themselves reviews. `neighbors` and `sample` show only candidates inside the strategy's publication-date limits (works outside them cannot be eligible); add `--any-date` only when an out-of-window work is wanted for vocabulary, and never in a blind benchmark, where the source review appears after the cutoff. Check candidates against eligibility with `screen BATCH WORK_ID include|exclude|unclear --reason "..."`. Citation neighbors require screening. Record whether each route depended on the starting search. If a protected record informs revision, run `develop KEY --reason "..."`.
4. **Vocabulary.** Use `terms` on development records, and `vocab keywords "..."` or `vocab topics "..."` to look up OpenAlex keyword alternatives (`alternatives`) and topic keyword lists (especially helpful in seedless runs or when seeds lack abstracts). Inspect development titles, reconstructed abstracts, recurring phrases and OpenAlex keywords. Consider synonyms, acronym ambiguity, spelling and indexing gaps. In seedless runs, avoid terminology echo chambers by also brainstorming older, pre-terminology, or discipline-specific labels (for example, `preprint*`, `e-print*`, or repository names alongside modern umbrella terms) and following `neighbors --direction references` on older papers to surface alternate phrasing. Start with `title-abstract`. Pilot keyword coverage by changing selected fields to `title-abstract-keywords`, rerunning and comparing both versions. OpenAlex keywords and topics are algorithmically assigned labels, not MeSH. A PubMed heading imported as text loses controlled-heading explosion. Spell out relevant alternatives. Keep term provenance and reasons for revisions in the critique or a workspace decision log.
5. **Run and revise.** Run `validate`, inspect the canonical OQL, then run `eval` (use `eval --quick` between revisions to skip the ablation lines and save requests; run a full `eval` before `review`) (add `--abstract-stats` to measure `% without abstract` for `final` and each search block and record missing-abstract attrition in `audit.md`). Both refuse a translation that changes the corpus (including inside a nested set) or drops a term or limit value. If that happens, rewrite the clause rather than accepting a weaker query. Check each block's count and known matches, the effect of dropping it (`without/ID`; with `combine`, also `drop-route/ID` for what each OR route adds), optional-block gains/losses, exclusion losses (`exclude/ID`), `irrelevant` match counts (screened-out development works still matched by `final`), and failures due to eligibility limits. A miss whose reason is `pulled` is a retracted, withdrawn or removed work that the default view leaves out; no vocabulary change recovers it, so report it rather than revise for it. Use `miss_details` for development misses: it gives the failing blocks, title, keywords and whether OpenAlex has an abstract. A miss with no abstract is an indexing gap; when `--abstract-stats` shows >15% missing abstracts or multi-block attrition (final `% without abstract` lower than individual blocks), actively pilot a conditional `has_abstract: false` fallback branch via `combine` (e.g. `"(a and b) or fallback_no_abs"` searching `title-abstract-keywords` or `fulltext`, or relaxing the second block for abstract-less works only) so volume stays low while recovering abstract-less studies. Compare result size and retrieval across revisions. When a block's count is unexpectedly large, run `term-counts --block ID` (about 10 credits per count): it flags bare words whose stem matches other words (`fasting` stems to `fast`: 471,555 titles stemmed vs 33,935 exact) and quoted hyphenated terms, which OpenAlex runs as an AND of their parts rather than a phrase (`"open-field"` 10,487 vs the phrase `"open field"` 4,872). Write the spaced phrase, which also matches the hyphenated spelling; `stemmed "risk-prone"` is already a phrase. Act on `strategy_warnings` in `validate` and `eval` output. Each `eval` after the first reports `revision` (count change, development works gained and lost, works per gained development work). Screen a seeded random sample (`sample --from-strategy --size 20`); `eval` and `report` turn the screened samples of the exact current search into a precision estimate with 95% intervals (strict, and counting unclear as eligible) and an estimated number of eligible records, which goes into `audit.md`. Screen it for ambiguous terms, excess workload, and OpenAlex abstract boilerplate (such as CC-BY license footers like *"open access article ... properly cited"* or repository *"Preferred citation:"* metadata that collide with broad single terms; replace colliding generic words with specific phrases or proximity). Revise one cause at a time and rerun. In thorough mode also try alternate concept boundaries and examine citation discoveries from both directions. Held-out answers live in the evaluation archive for final scoring. Keep them out of development. Record missing abstracts and unresolved identifiers. A zero denominator gives no recall estimate.
6. **Critique.** Give a fresh-context reviewer the question, eligibility, strategy, development-only CLI evaluation, sample decisions and limitations. Use a separate human reviewer when fresh agent context is unavailable. Ask them to assess the six domains shown below, including changes made or reasons for acceptance. Review the API warnings. A legacy URL conversion warning can coexist with valid OQL. Record substantive uncertainties. Resolve required revisions, reevaluate, and review the new evidence. Submit a JSON file with `review critique.json`. A fresh-context assessment by an agent is an internal PRESS-structured critique. Formal peer review is a human step.
7. **Deliver.** Run `report`. It reexecutes the query, checks the critique against the live search interpretation and known-paper matches, and saves a dated audit and validation evidence. Hand over the report path, query, count, coverage and relative recall by set with its 95% interval, unresolved identifiers, misses and limitations. Do not describe a recall estimate from a few known works without its interval. State the pulled-works line from the audit: how many retracted, withdrawn or removed works the search leaves out or includes. If `report` returns `post_exposure: true`, say that the exposed holdouts no longer give an independent estimate and quote the unexposed-set figures instead. For separately allocated holdouts, ask the independent reviewer to run the one-time `holdout-score` after delivery and report that aggregate separately. Explain that a dated rerun queries the current OpenAlex index. Point the reviewer to the draft PRISMA-S checklist at the end of `audit.md`: complete the items marked for the reviewer (registries, other sources, contacts, prior work, human peer review, cross-database deduplication) and check each filled item before reporting. Do not infer absolute recall from known-study retrieval. `eval` and `audit.md` also give a capture–recapture estimate of how many eligible works exist, from the overlap between works found by text routes (`sample`, `related`) and by citation routes (`neighbors` citing or references): low discovery completeness means keep discovering by both routes before trusting any development figure. It counts works by your own eligibility judgements, the routes are not independent (the bias can go either way) and overlaps are usually small, so report it with its interval and never as recall. In ten blind benchmark runs the agents included 36 of the 40 gold works they screened and excluded none, but discovery surfaced only 0–14 of each review's 26–28 included studies: the weakness is discovery reach, not screening. Widen discovery (more and more varied seeds, both citation directions, older and adjacent vocabulary) rather than tightening screening, and keep `unclear` for works that are genuinely borderline. **Always offer step 8 (optional no-abstract citation rescue)** right after delivering the Boolean search, explaining that works lacking abstracts in OpenAlex are disproportionately dropped by multi-block Boolean queries.
8. **Optional no-abstract citation rescue.** If the reviewer accepts, run `rescue --estimate` first (it states the credits; nothing runs), then `rescue`. The default `--direction cited-by --method references` finds the works the delivered set cites from their matched reference lists: it takes those lists from a complete `export` of the report if there is one (otherwise it pages the delivered search for IDs and references), keeps cited works outside the delivered set that lack an abstract and fall in the date window, then applies the any-block gate (or `--topic T...` when the review sits in 1–2 OpenAlex topics). It never rebuilds the search inside a citation query, so it does not time out; live on 2026-11-26 it returned exactly the citation query's result minus works already delivered. Its result is a dated ID list, because OpenAlex rematches references over time, and it can only reach works whose citing papers have matched reference lists. `--direction citing` (or `--method walk`) uses OpenAlex's citation-set query instead; `both` runs the two directions separately and reports an upper bound. Transient timeouts of that query are retried; if it still times out, relay the error's advice. Every rescue also saves `unlinked-references.json`: the printed reference lines of development works that OpenAlex could not link to a work, which are leads for other sources. Keep the supplementary rescue separate from the primary Boolean query in PRISMA reporting.
9. **Export.** When the reviewer wants the records, run `export` (and `export --rescue` if they also want the rescued abstract-less records, written to `exports/<report-id>-rescue/` for deduplication by OpenAlex Work ID). It pages the delivered query into `exports/<report-id>/results.{csv,ris,jsonl}`. Large result sets consume API budget: one request per 100 records. Run `export --estimate` first (free; it downloads nothing) and state the count, pages and expected credits and dollars, and use `--max-pages` for a bounded run if asked. If the manifest says `complete: false`, report the partial count and error. Then rerun `export` once the cause is fixed; it resumes from the saved cursor. Never present `results.partial.*` as complete. Report any `count_discrepancy` between the validated count and unique exported records.

## Separate-context holdout validation

Use this workflow when an independent human reviewer or a fresh-context agent can work in a directory **outside the development agent's accessible filesystem/context**. Do not copy its discovery batches, records, screening decisions, logs or holdout identities into the development workspace or transcript. Merely choosing different directories under the same unrestricted agent is not isolation. The CLI does not spawn agents or enforce OS permissions.

1. Initialise a separate reviewer workspace with the same question and eligibility. Copy only permitted development seed IDs and any date/corpus restrictions needed for discovery. In the reviewer context, use `neighbors` from those seeds and screen the candidates with `screen`. The reviewer must not share candidate metadata with the builder.
2. In the reviewer workspace, run `holdout-split --development-workspace PATH --seed 42` before the final strategy is delivered. It excludes works already discovered or registered in the development workspace, and conflicting decisions; deterministically divides the remaining eligible citation-discovered works approximately in half. It seals the allocation privately. Share only the command's development IDs and validation count with the builder; import the development IDs as `resolve --role relevant --source "independent reviewer discovery" ID ...`.
3. Develop, critique and deliver the Boolean search normally. Do not use the private holdout file, identities or results to optimise the strategy.
4. After `report`, have the independent reviewer run `holdout-score --report PATH` from the reviewer workspace. It checks that the report belongs to the designated workspace and was delivered after allocation, excludes holdouts independently rediscovered in the builder's recorded discovery or known-work files, resolves IDs again and scores the delivered query once. Share the aggregate score (and interval), not the private `blind-score.json` containing individual identities. For a revised strategy after exposure, allocate a fresh independent set. The score is a live-index relative recall estimate for citation-selected works, not absolute recall.

A local `validation` role is still useful for ordinary protected evaluation. The builder has filesystem access to local records and evaluation archives; local roles do not establish true blindness. If isolation cannot be arranged, explicitly report that limitation and do not claim blinded evaluation.

## Strategy format

Copy `examples/telehealth.json` as a starting point; `examples/telehealth-advanced.json` shows every option. Use an OR list of terms per block. Search blocks are ANDed unless `combine` is given. Optional blocks are tested individually alongside the core. Screen blocks stay in the scope table. Exclude blocks are ANDed as NOT. Use them sparingly, and only after checking `exclude/ID` for lost known works. Each block has a unique ID, role, field, terms and rationale, plus optional `"has_abstract": true|false` and `"topics": ["T10102"]` (allowing low-volume no-abstract fallback branches via `combine`, e.g. `"(a and b) or fallback_no_abs"`). Supported fields are `title`, `abstract`, `title-abstract`, `title-abstract-keywords` and `fulltext`. A term may be a single word, wildcard, quoted phrase or stemmed quoted phrase. In JSON, an exact phrase looks like `"\"remote care\""` and a stemmed phrase looks like `"stemmed \"remote care\""`. A proximity term is an object: `{"near": ["video", "consultation"], "within": 3}`. Its words are stemmed single words unless `"exact": true` permits phrases and wildcards. `"pulled"` is `exclude` (default) or `include`. `"corpus"` is `core` (default), `all` or `expansion`. Changing it changes the scope, so confirm it with the reviewer. `"combine"` is an and/or expression over every search block ID, for example `"(delivery or apps) and setting"`. Limits support ISO `from_date` and `to_date`, lists of `language`, `type`, and OpenAlex `topic` IDs, and boolean `has_abstract`. Preview the canonical interpretation when using wildcards, stemming, phrases or proximity.

## Offline draft mode

When the user asks for an untested/offline draft or has no OpenAlex API key, run `init`, author `strategy.json`, check it with `lint`, and generate `draft/draft-query.oql`, `draft/draft-notes.md` and `draft/draft-manifest.json` with `draft`. Neither command makes network calls. Clearly label the output **Untested draft — not validated against OpenAlex** and do not claim live counts or recall. To validate later in the same workspace, confirm scope (`scope --confirm`) and run `validate`, `eval`, `review` and `report`.

## Critique format

Supply a JSON object with text for `scope`, `vocabulary`, `boolean_and_fields`, `limits`, `retrieval`, and `limitations`. In each, describe the finding, supporting observation and disposition. Set `decision` to `ready` after addressing required changes. Do not type figures from earlier output: write placeholders such as `{final_count}`, `{development_recall}`, `{development_missed}`, `{pulled_count}` or `{without_abstract_pct}`, and `review` fills them in from the current evaluation (an unknown placeholder is refused and the message lists the available ones; holdout figures are not offered). `review` refuses a critique that quotes an earlier evaluation's final count but not the current one. The CLI records the evidence fingerprint and repeats evaluation on delivery.
