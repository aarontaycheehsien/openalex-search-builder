# OpenAlex Search Builder

Deliver a tested search strategy for human peer review. Use the Python CLI from this skill directory; every command takes `-w PATH` before the subcommand (`doctor` also runs standalone without `-w` to check API key and credit readiness). Every measurement must come from its JSON output. If an API call fails, identify the incomplete step and resume it. The evidence behind these rules is in `evals/RESULTS.md`; you do not need to read it.

1. **Intake.** Collect the question, eligibility criteria, required limits, optional known DOIs, PMIDs, PMCIDs or OpenAlex work IDs, and depth (quick, standard, thorough). If API connectivity or remaining budget is uncertain, run `doctor` first. Run `init --question "..." --eligibility "..." --depth standard`. For an update, use the existing workspace and inspect its last report and later changes.

2. **Scope.**
   - Propose a short table of concepts with their role (`search`, `optional`, `screen` or `exclude`) and rationale. Ask the reviewer to confirm or revise unless they have authorised proceeding.
   - Keep outcomes, methods and population restrictions at screening when searching them would lose eligible studies. Treat soft focus phrasing in the question or eligibility (*"especially in..."*, *"with a special focus on..."*, *"in particular..."*) as `screen` (or `optional`), not a mandatory `AND` block. Never AND an open-ended "any X" facet (any exposure, any outcome, any population) unless the single-concept search is genuinely unscreenable (over about 50k).
   - When a geographic region, setting or education/care level is genuinely required as a `search` block, include parent container terms (for example `Africa` and `"Sub-Saharan"` alongside southern African country names) so multi-country or regional studies are not dropped.
   - Do not apply hard `limits.type` filters such as `["article"]` or `["review"]`: OpenAlex frequently types systematic reviews as `article`, `book-chapter` or `conference-paper`, and primary studies as `conference-paper`, `report`, `dissertation` or `preprint`. Even for an umbrella review of reviews, combine review text terms with type rather than restricting `limits.type`. Set `limits.language` only when eligibility explicitly restricts language.
   - Calibrate volume to the topic: a narrow review may screen 1k–5k records, a broad one 15k–50k or more. Do not prune core synonyms just to meet a ceiling, and do not keep a broadening without evidence (step 5).
   - Put blocks and justified limits in `strategy.json` and eligibility in `protocol.json`. Choose the corpus with the reviewer (`core` by default, `all` to add the expansion corpus) and whether retracted, withdrawn and removed works stay out (`"pulled": "exclude"`, the default) or come in (`"include"`, for example to identify retracted studies).
   - Record the decision with `scope --confirm --note "..."`. Re-confirm after changing blocks or roles, the protocol, limits, corpus or the pulled setting; rewording a rationale needs no re-confirmation. A refused `eval` names what changed.

3. **Known works and discovery.**
   - Register known works with `resolve --role seed --source "reviewer" ID ...`. Ask the reviewer for known eligible studies whenever possible: in a seedless run discovery reaches few of the eligible studies, so known studies are the only reliable recall check. Without seeds in a quick run, proceed and document the gap.
   - If enough known papers are available, allocate a holdout before reading them or mining vocabulary, and register it as `validation`. Use `benchmark` only for included studies of a prior review that stay protected from development. In a blind benchmark, follow its intake rules and keep the source review inaccessible.
   - At standard and thorough depth, discover candidates:
     - `sample --from-strategy --top --size 20` screens the draft search's best matches first and is the most productive way to collect development works. `sample --oql 'get works where title-abstract has ("open access" and citation) and publication_date <= 2020-12-31' --size 15` pilots a query.
     - In seedless runs, also run `sample --from-strategy --prior-reviews --size 10` (or `--oql ... --prior-reviews`) to find pre-cutoff review papers with `referenced_works_count > 0`, and follow `neighbors REVIEW_ID --direction references` into primary studies. Works discovered from a review's reference list populate `eval`'s `independence.wording_independent` tier rather than echoing your draft keywords.
     - `neighbors ID ... --direction citing|references` follows citations from screened development works (several IDs rank co-linked candidates first; `--size`, `--all`, `--max-pages` and single-seed `--cursor` control paging). Links are OpenAlex's matched references, so older works, reports and theses are under-linked: follow `references` from recent open-access papers and `citing` from older ones. A seed with no links in that direction is refused. Keep snowballing while batches turn up eligible works.
     - `neighbors ID --direction related` returns at most 10 works by text similarity and never reviews or retracted works: treat it as a text route, and do not rely on it when the eligible studies are reviews.
     - Candidates are limited to the strategy's publication dates. Use `--any-date` only to look for vocabulary, never in a blind benchmark.
   - Screen with `screen BATCH WORK_ID include|exclude|unclear --reason "..."`, applying the eligibility criteria as written and keeping `unclear` for borderline works. Citation neighbours always need screening. Record whether each route depended on the starting search.
   - For blinded validation, use the separate-context workflow below before finalising the strategy. Without a separate reviewer, allocate newly screened candidates with `screen BATCH WORK_ID include --role validation --reason "..."` and call them protected, not blinded. Never relabel a development record as validation. If a protected record informs a revision, run `develop KEY --reason "..."`.

4. **Vocabulary.** Use `terms` on development records and `vocab keywords "..."` or `vocab topics "..."` for OpenAlex keyword alternatives and topic keyword lists. Read development titles, abstracts, recurring phrases and keywords; consider synonyms, acronym ambiguity, spelling variants and indexing gaps, and in seedless runs older, pre-terminology or discipline-specific labels. Start with `title-abstract`, then pilot `title-abstract-keywords` on selected blocks and compare. OpenAlex keywords and topics are algorithmic labels, not MeSH: spell out alternatives. Keep term provenance and reasons for revisions.

5. **Run and revise.**
   - Run `validate`, inspect the canonical OQL, then `eval`. Unchanged lines reuse `query-cache.json` across rounds (`--no-cache` forces a live rerun). Use `eval --quick` between revisions and a full `eval` before `review`; add `--abstract-stats` to measure missing-abstract attrition. Check `delivery_estimate` in `eval` and reserve at least `estimated_usd` for `report`, which always re-executes a full uncached evaluation. Both `validate` and `eval` refuse a translation that changes the corpus or drops a term or limit: rewrite the clause rather than accept a weaker query.
   - Read each block's count and known matches, `without/ID` (and `drop-route/ID` with `combine`), `with/ID` for optional blocks, `exclude/ID` losses, `independence` tiers (do not trust `0` losses on `without/ID` when `independence.warning` shows all development works are keyword-derived), `irrelevant` matches, limit failures and `strategy_warnings`.
   - Use `miss_details` for development misses. A miss with reason `pulled` cannot be recovered by vocabulary; report it. A miss without an abstract is an indexing gap: when `--abstract-stats` shows over 15% missing abstracts or attrition across blocks, pilot a `has_abstract: false` fallback branch through `combine` (for example `"(a and b) or fallback_no_abs"` on `title-abstract-keywords`, optionally gated with `"any_topics": ["T..."]`; prefer `keywords` over `fulltext`, as abstract-less works in OpenAlex carry keywords far more reliably than full text).
   - When a block is unexpectedly large, run `term-counts --block ID`. It flags bare words whose stem matches other words and quoted hyphenated terms, which OpenAlex runs as an AND of their parts: write the spaced phrase (`"open field"`), which also matches the hyphenated spelling.
   - A broadening must earn its records, and large searches (>10k, `large_result`) should check marginal term cost. When `eval` reports `revision.warning` (`broadening_without_gain` or `high_cost_broadening`), screen `sample --added --size 10` and keep the broadening only if it recovers a known work or adds eligible studies. When `large_result` or `high_cost_broadening` triggers, run `eval --term-impact` to inspect `records_only_here` and `development_only_here`: never auto-delete terms that directly name an eligible protocol concept just because `development_only_here` is empty; instead tighten broad single words into phrases or proximity and check `sample --removed --size 10` to confirm dropped records are off-topic.
   - Screen a random sample of the current search (`sample --from-strategy --size 20`): it gives the precision estimate in `eval` and the audit, and shows ambiguous terms and abstract boilerplate (licence footers such as *"open access article ... properly cited"*, repository *"Preferred citation:"* lines) colliding with broad terms; replace those with specific phrases or proximity.
   - Revise one cause at a time and rerun. In thorough mode also try alternate concept boundaries and both citation directions. Keep holdout answers out of development. A zero denominator gives no recall estimate.

6. **Critique.** Give a fresh-context reviewer, or a human when that is not available, the question, eligibility, strategy, development-only evaluation, sample decisions and limitations, and ask for the six domains in the critique format below with changes made or reasons for acceptance. Review the API warnings (a legacy URL-conversion warning can coexist with valid OQL). Resolve required revisions, re-evaluate and review the new evidence, then submit `review critique.json`. An agent's fresh-context assessment is an internal PRESS-structured critique; formal peer review is a human step.

7. **Deliver.**
   - Run `report`. It re-executes the query, checks the critique against the live interpretation and known-work matches, and saves a dated audit and validation evidence.
   - Hand over the report path, query, count, coverage and relative recall by set with its 95% interval, the precision estimate, unresolved identifiers, misses, limitations, and the audit's pulled-works line. Never give a recall figure from a few known works without its interval, and never infer absolute recall from known-work retrieval: in a seedless run, development figures measure vocabulary coverage, not recall. `capture_recapture` in `eval` output is a diagnostic; do not report it.
   - If `report` returns `post_exposure: true`, say that the exposed holdouts no longer give an independent estimate and quote the unexposed figures. For separately allocated holdouts, ask the independent reviewer to run `holdout-score` once and report it separately.
   - Explain that a dated rerun queries the current OpenAlex index. Point the reviewer to the draft PRISMA-S checklist at the end of `audit.md`: complete the items marked for the reviewer and check the filled ones.
   - Always offer step 8, explaining that works without an abstract in OpenAlex are disproportionately dropped by multi-block Boolean searches.

8. **Optional no-abstract citation rescue.**
   - If the reviewer accepts, run `rescue --estimate` (it states the credits and runs nothing), then `rescue`.
   - The default (`--direction cited-by --method references`) reads the delivered works' matched reference lists from a complete `export` of the report, or pages the delivered search for them, keeps cited works outside the delivered set that lack an abstract and fall in the date window, and applies the any-block gate (add `--keywords-gate` so abstract-less works can match OpenAlex keywords, `--min-links 2` when `co_citations` shows single-link rescue volume is too large, or `--topic T...` when the review sits in one or two OpenAlex topics). It does not time out. Its result is a dated ID list and reaches only works whose citing papers have matched reference lists.
   - `--direction citing` (or `--method walk`) uses OpenAlex's citation-set query, which can time out on large searches; relay the error's advice. `both` runs the two directions separately and reports an upper bound.
   - Each rescue saves `unlinked-references.json`: development works' reference lines that OpenAlex could not link, as leads for other sources. Report the rescue separately from the Boolean search in PRISMA.

9. **Export.** Run `export --estimate` first (free) and state the count, pages and expected credits and dollars; then `export`, which pages the delivered query into `exports/<report-id>/results.{csv,ris,jsonl}` (one request per 100 records; `--max-pages` bounds a run). `export --rescue` writes the rescued records to `exports/<report-id>-rescue/` for deduplication by Work ID. If the manifest says `complete: false`, report the partial count and error and rerun `export` once the cause is fixed; it resumes from the saved cursor. Never present `results.partial.*` as complete. Report any `count_discrepancy`.

## Separate-context holdout validation

Use this workflow when an independent human reviewer or a fresh-context agent can work in a directory **outside the development agent's accessible filesystem/context**. Do not copy its discovery batches, records, screening decisions, logs or holdout identities into the development workspace or transcript. Merely choosing different directories under the same unrestricted agent is not isolation. The CLI does not spawn agents or enforce OS permissions.

1. Initialise a separate reviewer workspace with the same question and eligibility. Copy only permitted development seed IDs and any date/corpus restrictions needed for discovery. In the reviewer context, use `neighbors` from those seeds and screen the candidates with `screen`. The reviewer must not share candidate metadata with the builder.
2. In the reviewer workspace, run `holdout-split --development-workspace PATH --seed 42` before the final strategy is delivered. It excludes works already discovered or registered in the development workspace, and conflicting decisions; deterministically divides the remaining eligible citation-discovered works approximately in half; and seals the allocation privately. Share only the command's development IDs and validation count with the builder; import the development IDs as `resolve --role relevant --source "independent reviewer discovery" ID ...`.
3. Develop, critique and deliver the Boolean search normally. Do not use the private holdout file, identities or results to optimise the strategy.
4. After `report`, have the independent reviewer run `holdout-score --report PATH` from the reviewer workspace. It checks that the report belongs to the designated workspace and was delivered after allocation, excludes holdouts independently rediscovered in the builder's recorded discovery or known-work files, resolves IDs again and scores the delivered query once. Share the aggregate score (and interval), not the private `blind-score.json` containing individual identities. For a revised strategy after exposure, allocate a fresh independent set. The score is a live-index relative recall estimate for citation-selected works, not absolute recall.

A local `validation` role is still useful for ordinary protected evaluation, but the builder can read local records and evaluation archives, so local roles do not establish true blindness. If isolation cannot be arranged, say so and do not claim blinded evaluation.

## Strategy format

Copy `examples/telehealth.json` to start; `examples/telehealth-advanced.json` shows every option.

- Each block has a unique `id`, `role`, `field`, `terms` and `rationale`, plus optional `"has_abstract": true|false`, `"topics": ["T10102"]` (primary topic only) and `"any_topics": ["T10102"]` (matches any of a work's three assigned topics; preferred over `topics` for no-abstract fallback branches). Search blocks are ANDed unless `combine` is given; optional blocks are tested one at a time; screen blocks stay in the scope table; exclude blocks are ANDed as NOT, so use them sparingly and only after checking `exclude/ID` for lost known works.
- Fields: `title`, `abstract`, `title-abstract`, `title-abstract-keywords`, `fulltext`.
- Terms: a single word, wildcard (at least three leading characters, not in a stemmed phrase), exact phrase `"\"remote care\""` or stemmed phrase `"stemmed \"remote care\""`. Proximity is an object, `{"near": ["video", "consultation"], "within": 3}`, of stemmed single words unless `"exact": true` allows phrases and wildcards.
- `"combine"`: an and/or expression over every search block ID, such as `"(delivery or apps) and setting"`. `"corpus"`: `core` (default), `all` or `expansion`. `"pulled"`: `exclude` (default) or `include`. Changing corpus or pulled changes the scope.
- `"limits"`: ISO `from_date` and `to_date`, lists of `language`, `type`, `topic` (primary topic IDs) and `any_topic` (any assigned topic IDs), and boolean `has_abstract`.
- Preview the canonical interpretation (`validate`) when using wildcards, stemming, phrases or proximity.

## Offline draft mode

When the user asks for an untested or offline draft, or has no OpenAlex API key, run `init`, write `strategy.json`, check it with `lint`, and produce `draft/draft-query.oql`, `draft/draft-notes.md` and `draft/draft-manifest.json` with `draft`. Neither command uses the network. Label the output **Untested draft — not validated against OpenAlex** and claim no live counts or recall. To validate later in the same workspace, confirm scope and run `validate`, `eval`, `review` and `report`.

## Critique format

A JSON object with text for `scope`, `vocabulary`, `boolean_and_fields`, `limits`, `retrieval` and `limitations`, each giving the finding, supporting observation and disposition, and `decision` set to `ready` once required changes are made. Do not type figures from earlier output: write placeholders such as `{final_count}`, `{development_recall}`, `{development_missed}`, `{pulled_count}` or `{without_abstract_pct}`, which `review` fills from the current evaluation (run `eval --abstract-stats` before `review` when budget allows, otherwise `{without_abstract_pct}` fills as not measured; unknown placeholders and holdout figures are refused). `review` refuses a critique that quotes an earlier evaluation's final count but not the current one. The CLI records the evidence fingerprint and repeats the evaluation on delivery.
